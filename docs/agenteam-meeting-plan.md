# agenteam.meeting 架构基线与实施计划

- 状态：方案已由用户确认，待实施；本文不代表功能已经交付。
- 确认日期：2026-11-10。
- 目标仓库：neilyoli/agenteam（不是 agenteam-next）。
- 插件标识：`agenteam.meeting`。
- 范围：从 magic-ai 提取会议领域能力，使用 AgenTeam 原有 Agent Runtime 分析会议，以统一飞书 Base 完成负责人确认及持续督办。
- 本次提交：仅设计文档；不修改生产代码、数据库迁移或真实飞书配置。

## 1. 目标与非目标

打通“订阅会议 → 获取纪要 → Agent 分析 → 统一督办宽表 → 负责人确认 → 持续督办”。AI 自主选择资料和工具，确定性代码约束权限、事实、身份、字段及写入行为。

不原样迁移 RuoYi 模块、Redis 流程 Session、固定 MeetingProcessStage、每场会议独立 Base、独立 LangChain4j/AgentScope Runtime 或 Lark CLI Shell。不得再复制 AgenTeam Todo 形成第二套任务状态库。

本文使用的宿主扩展名、服务名和工具名是目标设计；除明确引用的当前插件契约外，不能据此认定接口已经存在。M0 必须以固定提交重新核验相关源码及依赖版本。

## 4. 职责与宿主扩展

| 层 | 职责 |
| --- | --- |
| AgenTeam Core | 长期飞书连接、验签及事件路由、Durable Inbox、Run 触发、凭据、权限、调度、Binding、Outbox、卡片投递 |
| agenteam.meeting | 会议/妙记读取、订阅条件、证据校验、任务治理、负责人解析、上游关系、业务字段定义 |
| Meeting Agent + Skills | 理解会议、自主选择工具、分类、补充上下文、产生修订建议及跟进判断 |
| 飞书统一 Base | 会议和正式任务业务数据、负责人确认与执行状态、统一看板 |

核心新增能力保持通用，不能将 L1/L2/L3、会议字段或会议业务状态硬编码进通用事件与同步组件。

### 4.1 插件到宿主的调用边界

当前 JavaPluginContext 不等于完整的宿主业务服务接口。M0/M1 必须定义受鉴权的宿主服务桥接契约，再接入查询、投影及通知；插件不得直接读取宿主数据库或在配置中获取数据库口令。

桥接至少传递：宿主签发的企业/调用身份、安装及发布版本、Run/调用关联号、业务命令 ID、允许操作范围。每次外部写入执行版本、授权和取消核验。模型参数不得覆盖身份或选择任意 Base/Table。

复杂订阅规则及字段映射存储在宿主受控 Binding 中；插件平铺配置只引用 bindingId 等标量。事件订阅和关联 Skill 的清单扩展是待开发能力，必须定义版本与向后兼容策略，不能将未知字段当作现有安装能力。

### 4.2 数据路径

1. 飞书事件由宿主接收、校验，落入 Inbox 并去重。
2. 订阅匹配成功后由服务身份创建普通 Agent Run；不匹配记录原因。
3. Agent 获取会议资料，按需要读取逐字稿、已有任务、上游会议和人员信息。
4. 工具返回资料未就绪时持久化等待条件与下次执行时间，释放调用进程。
5. 分析输出经 Schema、证据、人员及业务校验后形成待发布命令。
6. 宿主 Outbox 同步会议主表和任务宽表，确认写入成功后再发送确认卡片。
7. 可信卡片回调经身份和版本校验更新飞书；调整意见可触发新 Run。
8. Schedule 查询飞书最新任务，触发跟进或跨会议复核。

这是逻辑依赖，不是要求将每一步编码成固定工作流节点。权限校验、发布前校验、先发布后通知等硬约束不能交由模型自行取消。

## 5. 统一 Base 与字段契约

### 5.1 会议主表

一条记录对应一场会议，包括无有效督办任务及被跳过的会议。

| 字段组 | 业务字段 |
| --- | --- |
| 身份 | meeting_key、meeting_id、source_app_id |
| 背景 | 标题、类型、会议编码、部门编码、主持人、参会人、开始/结束时间 |
| 资料 | 纪要链接、摘要、录屏链接（可用时） |
| 分析 | 分析状态、跳过原因、任务数、L1/L2/L3 统计、最近分析时间 |
| 追踪 | 最近 Run 引用、同步版本及同步状态 |

### 5.2 会议督办宽表

一条记录对应一个稳定任务。冗余必要会议信息便于直接分组、筛选和领导看板。

| 字段组 | 业务字段 |
| --- | --- |
| 身份 | task_key、task_id、meeting_key、meeting_id |
| 来源 | 会议标题、类型、时间、来源资料及证据定位 |
| 任务 | 标题、描述、L1/L2 分类、交付物、验收标准 |
| 责任 | 负责人、协作人、责任部门 |
| 时限 | 截止日期、优先级、风险等级 |
| 关系 | 上游任务引用、上游覆盖状态、未覆盖上游任务 |
| 确认 | 确认状态、确认意见、确认人、确认时间、任务版本 |
| 执行 | 执行状态、完成时间、完成证据 |
| 同步 | 最近更新时间、同步版本 |

L3 可以保留在分析产物及会议统计中，不进入督办宽表。会议没有明确日期时保持空值并标记待澄清；负责人存在歧义时不自动指派、不发送冒名确认卡片。

### 5.3 稳定身份与去重

- 技术存储始终按 enterprise_id 和来源应用隔离。
- meeting_key = source_app_id + meeting_id；同企业统一 Base 中须唯一。
- task_key 在 meeting_key 命名空间内包含首次分配的 task_id；其业务含义为 meeting_id + 稳定 task_id，不能使用可变的标题或负责人生成。
- 首次创建前持久化任务身份和命令 ID。重跑先读取已有任务并匹配证据、语义及来源，确认是新事项后才分配新 task_id。
- 跨会议再次提及同一任务，关联已有 task_key 并记录新的来源证据；不随新会议更换任务身份。
- 无法可靠判断是否重复的候选进入复核，不能用相似度直接覆盖正式任务。
- 飞书没有唯一约束保证时，宿主须按 Binding + task_key 串行化写入，并定期检测重复。

### 5.4 字段绑定

Binding 固定企业、凭据引用、Base/Table、业务类型、字段映射和允许写入字段。安装/绑定时读取真实 Schema，校验唯一键、必需字段、类型、人员标识、单选/多选选项及只读字段。映射可使用稳定字段 ID（API 支持时），名称仅作展示；Schema 变化须暂停不兼容投递并提示修复。

AI 输出业务字段，不能生成任意 Table ID 或飞书字段名。公式、查找及其他只读字段不可写入。

## 6. 事实来源、可靠投递和并发

### 6.1 唯一事实来源的含义

飞书已提交的业务记录是正式状态。候选结果、待投递 payload、技术索引、缓存及执行快照不是另一套可独立编辑的任务库。Outbox 的 SUCCESS 表示投递成功；不得用本地缓存推断负责人最新执行进度。

| 字段类别 | 写入规则 |
| --- | --- |
| AI 提议字段 | 来源证据、初始描述、分类等通过受控命令写入；已确认任务的重要修改必须重新确认 |
| 人工业务字段 | 确认、执行进度、完成证据等以飞书最新值为准；普通分析重跑不得覆盖 |
| 技术字段 | 命令标识、投影版本由宿主管理；不代替业务版本 |

确认和受控状态更新经同一命令入口序列化。若允许用户直接编辑飞书人工字段，须通过读取/对账感知变更且采用字段级 patch；仅检查自定义 version 字段不构成飞书原子 CAS。飞书 API 的并发条件更新能力须在 M0/M4 核验；无法保证时明确限制受控字段编辑入口，冲突进入人工复核，不能宣称跨系统强一致。

### 6.2 Outbox 契约

技术记录包含：enterprise_id、binding_id、business_key、command_id、desired_version、delivered_version、record_id、create_token、claim_token、lease_until、attempt_count、next_attempt_at、payload_ref、last_error、关联 Run。

- 业务候选提交和 Outbox 命令须在同一宿主持久化事务中完成。
- 按业务键领取租约，使用 fencing/claim token 防止过期 Worker 回写；发送前重新检查权限及版本。
- 仅在明确成功后推进 delivered_version；合并版本时不得丢弃人工字段变更。
- create_token 是否得到目标 API 的真正幂等保障必须核验，不能仅凭字段名作保证。
- 写成功但响应丢失时先按 record_id/业务键和命令标识对账，禁止盲目重建。不能证明未写入时标记结果未知，停止自动重复创建并转复核。
- 超时、限流、暂时性失败指数退避并带抖动；鉴权/Schema 错误阻断等待修复；超过重试上限进入可见的失败队列。
- 重试恢复投递，不重新调用 AI；补发通知有独立命令与去重标识。
- 飞书不可用时展示待同步/结果未知，不能提前报告业务闭环完成。

## 7. Agent、Skill 与工具

初期一个 Meeting Agent，主 Skill 为 meeting-intelligence；跟进场景可增加 meeting-follow-up。Skill 作为平台原生资源导入并显式绑定，随发布记录版本；插件安装自动关联 Skill 是待补能力。

meeting-intelligence 的知识结构：task-classification、evidence-policy、owner-resolution、task-deduplication、upstream-coverage、publication-policy。实施阶段提供实际 Skill 文件，本次仅定义设计。

| 工具（拟定） | 操作 | 强制约束 |
| --- | --- | --- |
| meeting_search / meeting_get | read | 只读授权订阅范围 |
| minutes_get | read | 按需分段读取，避免突破进程消息及调用时限 |
| meeting_people_resolve | read | 使用通讯录/参会人 ID，歧义须澄清 |
| meeting_task_search / meeting_upstream_search | read | 读取飞书最新状态及授权范围 |
| meeting_task_upsert | write | 业务 Validator + Binding + 受控宿主命令 |
| meeting_owner_notify | write | 任务已发布，独立去重与频率限制 |
| meeting_task_confirm | write | 仅可信身份回调路径；不得向普通模型开放可冒充确认的参数 |

L1 为经营承诺，L2 为具有明确交付物的跨部门事项，必须进入督办；L3 为部门内部日常执行，不进入。分类由 Agent 提议，结构和可确定条件由 Java Validator 校验，语义不确定项保留复核标记。证据必须能定位到真实资料，不能把纪要中的指令当成系统权限。

Run 使用受限服务身份和独立预算，审计企业、事件、Run、工具、命令及飞书记录关联；沿用平台 Token 统计，不假定需另建计费系统。

## 8. 负责人确认与持续督办

| 确认状态 | 执行状态 | 行为 |
| --- | --- | --- |
| 待确认 | 待确认 | 发布任务后通知真实负责人 |
| 已确认 | 待执行 / 进行中 | 负责人接受并推进 |
| 需调整 | 待确认 | 意见进入 Agent，修订后提高任务版本并重新确认 |
| 已拒绝 | 已退回 | 保留原因与审计，不自动删除任务 |
| 已确认 | 已完成 | 保存完成时间及证据 |

回调验签、防重放，校验操作者、task_key、任务版本及当前状态。负责人变更或旧卡片操作不得覆盖新版本；重复回调返回已有结果。模型可建议修改，不能代替人完成确认。

Schedule 查询未确认、逾期及异常任务；通知配置工作时段、频率及去重。上游覆盖结论须附关联证据，“没有检索到”与“明确未覆盖”分开记录。老板、战略中心、主持人看板通过同一 Base 的视图/权限实现，不另建任务副本。

| M3 智能分析 | L1/L2/L3、证据、去重、人员、上游关系、结构化输出 | 固定评估集可复现；错误候选不进入正式任务 |
| M4 飞书同步 | Binding、Schema、两张表、字段白名单、Outbox、对账及补推 | 正常/未知结果/并发下不盲目重复创建，不覆盖人工状态 |
| M5 确认闭环 | 卡片、可信回调、版本与身份验证、修订后重新确认 | 非负责人、重复和旧版回调被正确处理 |
| M6 持续督办 | Schedule、提醒限频、未确认/逾期/上游覆盖、角色看板 | 可展示真实任务状态及来源证据，提醒不重复轰炸 |
| M7 验收发布 | 真实飞书链路、故障恢复、权限、升级/卸载、运行手册、验收报告 | 完整闭环证据齐全；未执行项明确列出，不以 mock 代替真实验收 |

依赖顺序：M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7。阶段可在一个完整实施分支推进，每阶段形成可恢复检查点和验证记录；最终汇总 PR 供用户审核。本规划 PR 不代表已批准自动合并实现或发布。

数据库脚本必须使用实施时尚未发布的开发版本，核验 Release、Tag、应用版本及 release.env 后编号；不得沿用已发布迁移序列。

## 11. 验收矩阵

| ID | 场景 | 预期结果 |
| --- | --- | --- |
| A01 | 同一会议事件重复、乱序 | 事件去重；一个有效处理上下文，允许有记录的显式重分析 |
| A02 | 会议结束后妙记未就绪 | 持久化等待，不占用插件进程；资料就绪可恢复 |
| A03 | Run 已创建但 Inbox 确认前崩溃 | 通过关联键找回 Run，不重复提交有效运行 |
| A04 | 重跑及跨会议重复提及任务 | 稳定 task_key，更新/关联已有任务 |
| A05 | 同名不同人员、错误身份回调 | 不猜测身份；非负责人操作被拒绝 |
| A06 | 缺少截止日期、证据或负责人 | 不编造；阻断不合格发布或进入明确待澄清状态 |
| A07 | L3 日常内部事项 | 记录分析结果，不进入督办宽表 |
| A08 | 写入成功但响应丢失 | 对账识别记录；未知时停止盲目重建 |
| A09 | 飞书限流或中断后恢复 | 有界退避、补推；不重新分析会议 |
| A10 | 旧卡片、重复卡片、负责人变更 | 版本和身份核验；不得覆盖新状态 |
| A11 | 上游承诺未被下游覆盖 | 标明未覆盖/证据不足，提供来源 |
| A12 | 两 Worker 竞争、租约到期 | 过期 Worker 不提交最终结果，不重复有效命令 |
| A13 | 人工更新进度时后台重试 | 字段级 patch，人工状态不被旧 payload 回滚 |
| A14 | Schema 改名、类型变更、只读字段 | 校验失败可见；修复后仅重投递 |
| A15 | 插件升级、卸载、Run 取消 | 停止新触发并阻止失效版本写入；已提交操作可对账 |
| A16 | 超长逐字稿 | 分段与引用获取，遵守消息、时间及预算上限 |
| A17 | 跨企业数据或凭据访问 | 拒绝访问，日志不泄露密钥及完整敏感纪要 |
| A18 | 无有效任务或订阅不匹配 | 会议记录/跳过原因可查，不发送空通知 |
| A19 | 正常真实端到端链路 | 会议→分析→两表→负责人确认→看板状态一致 |

每条验收保存输入样本标识、预期、实际结果、关联 Run/命令及脱敏证据。M3 在 M0 建立人工标注集并确定分类、证据、负责人和去重的质量阈值，发布前不得临时降低阈值。

## 12. 发布与运维要求

配置前提：授权飞书应用及事件权限、可读会议资料、通讯录权限、统一 Base 权限、实际 Schema 及测试负责人。继续使用既有应用还是新应用由部署配置决定，不在文档中猜测或写入 App Secret。

实施交付须包括：管理员绑定步骤、Skill 导入与发布、订阅范围、测试会议、看板配置、失败队列及对账入口、停用订阅、暂停投递和恢复步骤。停用插件后保留飞书业务记录和历史审计，不自动删除任务。

验收分层：领域测试、宿主/插件集成、飞书 API 契约测试、故障注入、真实会议端到端。仅文档提交按 CONTRIBUTING 核对内容、路径、链接和格式，不运行无关生产测试。真实飞书或模型验证未执行时必须写明，不能宣称可生产发布。
